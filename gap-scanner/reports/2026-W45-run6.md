### Unit: listener (spec §2.1, `http_service_endpoint.bal`, `http_default_listener.bal`, native listener/endpoint)

| Topic | Verdict |
|---|---|
| Read/write/idle/header timeouts per phase | **Gap filed** (`listener-separate-keepalive-idle-timeout`). A single `timeout` covers keep-alive idle, request receipt and handler execution. The sample `single_timeout.bal` shows a 5s handler getting `408` with `timeout = 3`. Related upstream issues ballerina-library#2906 (open) and #4102 ask for handler interruption, which is a different request. |
| Header-read timeout (slowloris) | Effectively present: the listener drops a connection whose headers trickle in. The sample `slow_headers.bal` (timeout 3s, one header line every 2s) saw the connection closed after about 6s (client got SIGPIPE, exit 141). This is because the idle handler sits after `HttpRequestDecoder` ([Util.java#L851-L857](https://github.com/TharmiganK/module-ballerina-http-agents/blob/ad64ade67e37abdff15fba06fd8f40e74dcd269e/native/src/main/java/io/ballerina/stdlib/http/transport/contractimpl/common/Util.java#L851-L857)), so partial header bytes are not counted as activity. That contrasts with spec §2.1.5, where body chunks are counted. The header behaviour is protective and not documented. Not handed off as a defect because it is plausibly intended; the spec could mention it. A separately configurable header timeout is covered by the proposal in the filed finding. |
| Graceful shutdown with drain deadline | Already reported: TharmiganK#93 \"`gracefulStop()` should drain in-flight requests instead of sleeping for the whole timeout\", plus the question issue \"Should `gracefulStop()` serve in-flight requests by default?\" and the `immediateStop()` restart issue. Not refiled. |
| Connection limits (max concurrent connections) | **Gap filed** (`listener-max-concurrent-connections`, low demand). No such option in `ListenerConfiguration`/`ServerSocketConfig`, and `ServerConnectorBootstrap` sets no limit. |
| Request-size limits (URI, header size, body, HTTP/2 streams) | Present: `requestLimits.maxUriLength`, `maxHeaderSize`, `maxEntityBodySize`, `http2MaxActiveStreams`. A max header *count* (Node.js `maxHeadersCount`, Kestrel `MaxRequestHeaderCount`) is absent but adds little beyond `maxHeaderSize`; not filed. Limits on HTTP/2 bodies are a defect matter (spec says they are not checked) and out of scope here. |
| Port 0 with bound port readable | Already decided: TharmiganK#51 was closed by the maintainer. Port 0 stays rejected until there is a way to read the bound port. The sample `port0.bal` confirms `error: Listener port is not defined!`. Not refiled. |
| Binding to several addresses / Unix domain sockets | Absent (one `host` and port per listener). Several addresses can be served by declaring several listeners and attaching the same service, which is a reasonable workaround. Unix sockets have no upstream demand and an unclear fit for Ballerina deployments. Not filed. |
| Server-wide hooks (connection open/close, shutdown callbacks) | Absent as hooks. Lifecycle is driven by the Ballerina listener model (`gracefulStop`, module-level `on fail`/shutdown); per-request interception exists through interceptors. There are no requests and the fit with the listener object model is weak. Not filed. |
| Keep-alive and max requests per connection | `keepAlive` AUTO/ALWAYS/NEVER is present. Max requests per connection (Tomcat `maxKeepAliveRequests`, Node.js `maxRequestsPerSocket`, `Keep-Alive: max=`) was asked for in upstream ballerina-library#371 and closed as not the common case. Not refiled. |
| Default listener | Present (`getDefaultListener()`, configurable via Config.toml). No gap. |
| Listener host and port accessors | `getPort()`/`getConfig()` are present (upstream \"Need to Access Host and Port from the Listener\" is resolved). |

### Coverage

Unit: service-dispatching (spec §2.2, 2.3.1–2.3.3, 3, 4.1, 4.2; `ResourceDispatcher`, `ResourceDataElement`, `DispatcherUtil`, `HttpDispatcher`, `http_annotation.bal`).

Sample run: `agent-scratch/dispatch.bal` (a GET+POST resource, an `[int id]` path param, a `produces` resource, and a service with `host: "example.com"`). Results:
- `HEAD /api/items` → 405.
- `PUT /api/items` → 405, no `Allow` header.
- `OPTIONS /api/items` → 204, `Allow: GET, POST, OPTIONS`.
- `/api/items/abc` against `[int id]` → 400.
- `Host: example.com` → 200; `Host: example.com:9555` → 404; default Host → 404.

Topics:
- **Automatic HEAD for GET resources:** gap, already reported as #90 (open; follows #56). Confirmed by the sample (HEAD → 405). Not filed.
- **Automatic OPTIONS:** present. `ResourceDispatcher.handleOptionsRequest` returns 204 with `Allow`. The query-string base-path case is already reported in known issues.
- **405 with `Allow`:** gap, filed as `405-response-allow-header` (RFC 9110 §15.5.6 MUST; Go, Spring, Jersey and ASP.NET Core all send it). No existing issue found.
- **Route constraints and typed segments:** present. `int`, `float`, `boolean` and `decimal` path params, plus constraint annotations on path params (upstream #3239/#4371 closed as done). Ballerina does not allow two resources that differ only by segment type (`get items/[int id]` and `get items/[string name]` is a compile-time "redeclared symbol" error), so ASP.NET-style constraint fall-through doesn't fit the module. Not applicable.
- **Parse failure status:** the spec says 500 and the listener returns 400; already reported in known issues ("Spec §2.3.3 says path param conversion failure returns 500…").
- **Constraint errors:** wrong error type for path-param constraint violations, already reported in known issues.
- **Wildcard and catch-all segments:** present. Rest params `[string... s]` and the `'default` accessor. Zero-segment rest matching is already reported in known issues. Mid-path wildcards are not common enough in the reference libraries to count as a gap.
- **Host matching:** present (`ServiceConfig.host`, exact match against `Host`). The port/case mismatch I reproduced is already reported ("ServiceConfig `host` is not matched when the Host header contains a port or differs in case"). Wildcard hosts (ASP.NET `RequireHost("*.x")`) are rare; not filed.
- **Header matching:** not filed. Only Spring `headers=` offers it in routing, and it is rarely used. Interceptors or a header param cover the need.
- **Media-type matching:** two resources with the same path and method but different `produces` are impossible at the language level (redeclared symbol). Server-side content negotiation is already requested upstream as ballerina-library #280 (open). Not filed.
- **Route introspection and generated links:** present. Introspection/OpenAPI resource, `Link` header on OPTIONS, and HATEOAS `linkedTo` (proposal `introducing-initial-support-for-hateoas.md`).
- **Versioned routes:** present through base paths per service (`/v1`, `/v2`) and service contract `basePath`. Header- or media-type-based versioning would depend on content negotiation (#280). Not filed.
- **Custom methods:** present (custom accessors). The QUERY method is already requested upstream as ballerina-library #8873.
- **Trailing slash:** present; `sanitizeSubPath` normalises it.

No handoffs: every suspected defect I saw (Host with a port, the §2.3.3 400-vs-500 mismatch) is already reported.
