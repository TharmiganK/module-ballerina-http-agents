### Candidates dropped
- **Stale entry stays stale after a 304 revalidation (cached Age is never reset)**: my first hypothesis. The first scanner_2_1 test (304 revalidation, then a cache hit) passed. The scratch trace showed the Age does reset, because of the seconds/milliseconds mix-up reported as finding 1. Not a separate defect.
- **`HttpCache` `addEntry` appends every full (200) revalidation response to the per-key `Response[]` without dropping older ones** (`caching_http_cache.bal` L176-187, called from `getValidationResponse` L66). Memory per key grows while the key stays in use, although the comment says "replace the stored responses". It cannot be observed from a test package (`HttpCache.cache` is module-private, and memory growth is not reliably assertable), so it is not reported. Upstream library#989 (closed) was about the cache capacity default, not this.
- **Revalidation error path**: when the origin is unreachable, `getValidationResponse` sets `Warning: 111` on the cached response but returns the `ClientError` instead of the stale response, contradicting its comment. RFC 7234 allows returning the error, so the visible behaviour is acceptable. Dropped as dead code, not a user-visible defect.
- **Expired cookie (`Expires` in the past) not removing an existing session cookie when no persistent handler is configured**: same area as #27 (Max-Age=0 deletion, which has a fix in progress) and #26. Dropped as covered or too close.
- Cache key excludes the host and `Vary`: duplicate of #60. Server-side conditional requests and unquoted ETags for `@http:Cache` (§4.6): duplicate of #59.
